| Code | Language | Direction |

| `en` | English  | LTR       |
| `ar` | Arabic   | RTL       |

- All 4 translation JSON files (`en.json`, `ar.json`, `fr.json`, `de.json`) in `assets/translations/` must have **identical keys**, grouped by section (`nav`, `hero`, `about`, `skills`, `projects`, `experience`, `contact`, `footer`, ...).

- RTL is automatic when `locale = ar` — never set `Directionality` manually. Test every layout in both LTR and RTL.
- Register `assets/translations/` in `pubspec.yaml`.

## 🧠 State Management — BLoC / Cubit

**Only `flutter_bloc` is used. Riverpod and Provider are forbidden.**

- Use **Cubit** for simple state (theme toggle, locale switch, scroll tracking).
- Use **BLoC** (with events) for complex async flows (form submission, data fetching).
- Every Cubit/BLoC lives inside its feature's `presentation/bloc/` folder; states/events extend `Equatable`.
- Global cubits are provided at the app level in `app.dart` via `MultiBlocProvider`; feature-local cubits are provided at the page level via `BlocProvider`.
- Theme is managed by `ThemeCubit` in `core/theme/theme_cubit.dart` (default `ThemeMode.dark`).
- Use `BlocBuilder` to read state, `BlocListener` for side effects (snackbars, navigation), `BlocConsumer` for both.

## 🎨 Design System

- **Breakpoints:** `Breakpoints.mobile = 600`, `Breakpoints.tablet = 1024`, `Breakpoints.desktop = 1280`, defined in `core/constants/app_sizes.dart`. Always resolve layout via `LayoutBuilder` or `ResponsiveWidget` — never raw `MediaQuery.of(context).size.width` in feature widgets.
- **Colors:** all tokens live in `core/constants/app_colors.dart` (`background`, `surface`, `primary`, `accent`, `textPrimary`, `textSecondary`, `border`). No hex literals outside this file.
- **Typography:** all `TextStyle`s live in `core/constants/app_fonts.dart`, built from three local font families (`SpaceGrotesk` for display, `Inter` for body, `JetBrainsMono` for labels). **All fonts are local assets, declared in `pubspec.yaml`** — no `google_fonts`, no network font loading, ever.
- **Spacing scale:** use only `4, 8, 12, 16, 24, 32, 48, 64, 80, 96, 128`.

## ♿ Accessibility — Non-Negotiable for Web

> Accessibility is in the **Decision Hierarchy above animation and visual complexity.**
> A portfolio that looks stunning but fails a screen reader or keyboard check is not production-ready.
> Target: **WCAG 2.1 AA compliance** as the minimum bar.

### Rules

1. **Semantic widgets over generic containers.** Clickable actions use `ElevatedButton`/`TextButton`/`IconButton`, never a bare `GestureDetector`. Section titles get `Semantics(header: true)`; decorative images use `ExcludeSemantics`; meaningful images get a `Semantics(label: ...)`.
2. **Icons need labels.** Every `IconButton` and meaningful standalone icon has a `tooltip` and/or `semanticLabel`. Purely decorative icons are wrapped in `ExcludeSemantics`.
3. **Full keyboard navigation.** Every interactive element reachable via `Tab` in logical order; `Enter`/`Space` trigger actions. Modal dialogs (gallery, CV viewer) trap focus and restore it on close. Gallery responds to `ArrowLeft`/`ArrowRight`; menus close on `Escape`.
4. **Visible focus rings**, always — never suppressed via `overlayColor`/`BorderSide.none` on the focused state. Define focus styles globally in `app_theme.dart`.
5. **Color contrast** meets WCAG 2.1 AA: **4.5:1** for normal text, **3:1** for large text/UI components. Verify every text/background pair in both themes; document the ratio next to each color token in `app_colors.dart`.
6. **Never convey state by color alone** (active/error/selected) — pair it with an icon, underline, weight, or text.
7. **Reduced motion.** A `shouldAnimate(context)` helper (gated on `MediaQuery.of(context).disableAnimations`) in `core/utils/responsive.dart` must gate every animation site. Also respect the OS-level `prefers-reduced-motion` media query in `web/index.html`.
8. **No text embedded in images** — always real `Text` widgets, except inherently image-based logos/brand marks (which still need a `semanticLabel`).
9. **Landmark structure** via `Semantics` — `header: true` on section titles, `namesRoute`/`label` on the nav region, `container: true` on the main content region.

### Checklist — before any section is marked done
- [ ] Fully keyboard-operable (Tab + Enter/Space).
- [ ] All `IconButton`s have a `tooltip`.
- [ ] Meaningful images have `semanticLabel`; decorative images are excluded.
- [ ] Focus ring visible everywhere, both themes.
- [ ] Contrast ≥ 4.5:1 normal / ≥ 3:1 large text.
- [ ] State never conveyed by color alone.
- [ ] No text embedded in images.
- [ ] `shouldAnimate()` gates every animation.
- [ ] Modals trap and restore focus.
- [ ] Tested with Flutter's built-in screen reader (DevTools → Accessibility).

### ❌ Anti-patterns — strictly forbidden
- ❌ `GestureDetector` on a primary action instead of a proper button widget.
- ❌ `IconButton`/icon without `tooltip` or `semanticLabel`.
- ❌ Suppressed focus rings.
- ❌ State conveyed by color alone.
- ❌ Text embedded in image assets.
- ❌ Animations that ignore `disableAnimations`.
- ❌ Modals that don't trap/restore focus.
- ❌ Tab order that doesn't follow the visual reading order.

## 🎞️ Animation Rules

> Animations must be **intentional, purposeful, and never compromise readability, accessibility, or performance.**
> Rich animation is reserved for high-impact zones. Subtlety is correct everywhere else.

### Decision Hierarchy

When any animation requirement conflicts with another concern, resolve it in this order — it's absolute:

1. **Accessibility** — `disableAnimations` set? Skip everything.
2. **Performance** — drops below 60fps? Cut the animation, not the frame rate.
3. **Usability** — obscures content or delays interaction? Remove it.
4. **Visual consistency** — clashes with the design system? Revise it.
5. **Animation complexity** — only after all the above, add richness.

### Animation Tiers

**Tier 1 — Rich animation zones:** Hero, Project Cards, Navigation, Project Details, CTA Buttons. These carry the visual identity — use strong, orchestrated motion (staggered entries, hover states, ceremony).

**Tier 2 — Design-appropriate animation:** About, Skills, Experience, Contact, Footer. A single `VisibilityDetector`-triggered `fadeIn + slideY` per section is enough — no stacking, no forced "signature" motion. Grid/list items may stagger 60–80ms per item, but only if the item count is ≤ 8; beyond that, animate the container instead.

### Timing Standards

| Animation Type              | Duration     | Curve              |
|-----------------------------|--------------|--------------------|
| Tier 1 — section/hero entry | 500–700ms    | `easeOutCubic`     |
| Tier 2 — section entry      | 400–500ms    | `easeOut`          |
| Stagger delay per item      | 60–80ms      | —                  |
| Hover scale / shadow        | 200–250ms    | `easeOutCubic`     |
| Nav active indicator slide  | 250–300ms    | `easeOutCubic`     |
| Typewriter per character    | 70–90ms      | —                  |
| Page route transition       | 300–350ms    | `easeInOut`        |
| Lottie ambient (Hero only)  | per JSON     | repeat: true       |

### Performance Rules

- **60fps is the floor**, not the target. Profile before shipping any Tier 1 animation.
- Wrap heavily animated widgets in `RepaintBoundary`.
- **Maximum 2 simultaneously looping animations** on screen at any time.
- Lottie files must be **under 150KB** each.
- `shouldAnimate(context)` (see Accessibility → Reduced Motion) must gate every animation site.

### Required Packages
`animate_do`, `flutter_animate`, `visibility_detector`, `lottie` (Hero only), `animated_text_kit` (Hero only). See **Dependencies** above.

### ❌ Anti-patterns
- ❌ Tier 1 intensity applied to Tier 2 sections.
- ❌ More than 2 looping animations visible simultaneously.
- ❌ Animations that ignore `disableAnimations`.
- ❌ Sub-60fps animations shipped to production.
- ❌ Staggering more than 8 items individually.
- ❌ Linear easing on user-facing motion.
- ❌ Content display delayed beyond **800ms** from section entry.
- ❌ Hover effects on mobile (use tap feedback instead).

## 🚨 RESPONSIVENESS — NON-NEGOTIABLE

> **Every single UI component built in this project MUST be fully responsive.**
> This is not optional. A UI that breaks on any screen size will be rejected.

### Supported Screen Sizes

| Target      | Width Range         | Breakpoint Constant       |
|-------------|---------------------|---------------------------|
| Mobile      | < 600px             | `Breakpoints.mobile`      |
| Tablet      | 600px – 1024px      | `Breakpoints.tablet`      |
| Laptop      | 1024px – 1280px     | `Breakpoints.desktop`     |
| Desktop     | > 1280px            | `Breakpoints.desktop`     |

### The One Rule
Every widget → `LayoutBuilder` first, design second. Resolve mobile/tablet/desktop branches through `LayoutBuilder`'s `constraints.maxWidth`, or through the shared `ResponsiveWidget` helper in `core/utils/responsive.dart` (takes `mobile`/`tablet`/`desktop` widgets and picks one against `Breakpoints`).

### Responsive Rules Per Section

| Section    | Mobile                            | Tablet                          | Desktop                        |
|------------|-----------------------------------|---------------------------------|--------------------------------|
| NavBar     | Hamburger menu (Drawer)           | Hamburger or compact links      | Full horizontal links          |
| Hero       | Stacked (text above, image below) | Stacked with larger text        | Side-by-side (text + avatar)   |
| Skills     | 2-column grid                     | 3-column grid                   | 4–5 column grid                |
| Projects   | 1 card per row                    | 2 cards per row                 | 3 cards per row                |
| Experience | Vertical timeline, full width     | Vertical timeline, 80% width    | Alternating left/right timeline|
| Contact    | Stacked fields, full width        | Single column, 70% width        | Two columns (form + info)      |
| Footer     | Stacked, centered                 | Stacked, centered               | Horizontal, space-between      |
| Gallery    | Full-width swipe cards            | 2-per-row grid                  | 3-per-row grid + lightbox      |
| Video      | Full width, 16:9 ratio            | 80% width, centered             | 60% width, centered            |
| CV Buttons | Stacked full-width buttons        | Side-by-side buttons            | Side-by-side buttons           |

- Font sizes scale with screen size via helpers in `core/constants/app_fonts.dart` — never a single fixed size across all breakpoints.
- Horizontal page padding shrinks on smaller screens via a helper in `core/utils/responsive.dart` (mobile 16px / tablet 32px / desktop 80px, as a starting point).

### Responsive Checklist — before marking any task done
- [ ] Mobile (360px–599px) — no overflow, no clipped text, no broken layout
- [ ] Tablet (600px–1023px) — layout adapts, spacing feels right
- [ ] Laptop (1024px–1279px) — desktop layout scales down gracefully
- [ ] Desktop (1280px+) — content isn't stretched full-width on ultra-wide screens

Use Flutter DevTools' device toolbar or `flutter run -d chrome` and resize manually.

### ❌ Anti-patterns — never do these
- ❌ Fixed pixel widths on containers — use `constraints.maxWidth` fractions.
- ❌ Hardcoded font sizes without breakpoint checks.
- ❌ `Row` with many children and no `Flexible`/`Expanded`.
- ❌ `MediaQuery.of(context).size` inside a non-root widget — use `LayoutBuilder`.
- ❌ Overflow ignored (`clipBehavior: Clip.none`) as a "fix".
- ❌ One layout for all screen sizes with only padding changes.
- ❌ Skipping mobile layout because "it's a web app."

## 🎬 Media Rules — Video, Photos & PDF

### Asset Folders
See the `assets/` tree in **Project Structure** above for the full layout (`images/`, `videos/`, `pdf/`). Register all new folders in `pubspec.yaml`.

---

### 🖼️ Images — Performance Rules

> Images are the single biggest performance risk on a portfolio site. Treat this with the same weight as the animation Decision Hierarchy's Performance rule.

- Prefer **WebP** (or **AVIF** where supported) over PNG/JPEG for photos and screenshots.
- **Never ship huge, uncompressed PNGs.** Compress every project screenshot before it goes into `assets/`.
- Use the **appropriate resolution** for where the image is actually displayed — don't ship a 4K screenshot for a 400px card.
- **Never load full-resolution images in the projects grid.** Each card renders a dedicated, compressed `thumb.png`/`thumb.webp`; full-resolution `screenshot_N` assets load only inside the gallery, on demand.
- Apply the same rule to `avatar.png` and any decorative/background images.

---

### 📸 Project Photos (Image Gallery)

**Package:** `photo_view`. **Widget location:** `features/projects/presentation/widgets/project_gallery.dart`.

- Every project card shows only `thumb.png`.
- Tapping the card / "View Gallery" opens a fullscreen `PageView` gallery (`Dialog` or `/project/:id/gallery` route).
- Images lazy-load with a fade-in; support keyboard arrow navigation for web.
- Show an image count indicator: `1 / 3`.
- The `ProjectModel` (`features/projects/data/models/project_model.dart`) carries `thumbAsset`, `screenshotAssets`, and an optional `videoAsset` — see **Data Layer** above.

---

### 🎥 Project Video Player

**Package:** `chewie` (wraps `video_player`). **Widget location:** `features/projects/presentation/widgets/project_video_player.dart`.

- Video is **optional** per project — only render the player if `videoAsset != null`.
- Always show a poster/thumbnail before the video initializes.
- Controls required: play/pause, seek bar, mute, fullscreen toggle.
- `VideoPlayerController` is created and disposed inside a `VideoPlayerCubit` (`features/projects/presentation/bloc/`) that manages loading/ready/error states — dispose the controller in the cubit's `close()`.
- **Never autoplay** — the user must tap play explicitly.
- **Never pre-initialize.** `autoplay: false` alone is not enough — it only stops playback, not loading. The controller must not be constructed or `.initialize()`'d until the user opens the project's detail view/gallery, or taps play.
- **Never initialize video on the home page.** `projects_section.dart`'s grid shows `thumb.png` only for every card — never a video player, never a hidden/paused controller. Video initialization only happens in `Project Details`.
- Only `mp4` is supported (best cross-browser web compatibility); use `VideoPlayerController.asset(path)` for local assets.

### 📄 CV — View & Download (PDF)

**Packages:** `pdfx` (inline Web-compatible viewer) + `url_launcher`/conditional download helper. **Feature folder:** `features/cv/`.

- CV file lives at `assets/pdf/cv.pdf` — **one file, never duplicated**.
- Hero/About shows two buttons: **"View CV"** (opens an in-app viewer, `Dialog` or `/cv` route) and **"Download CV"** (triggers a browser download).
- Show a loading indicator while the PDF is read, and a page indicator (`Page 1 of 3`).
- State is managed by `CvCubit` (`features/cv/presentation/bloc/cv_cubit.dart`) with initial/loading/ready/error states.

#### Download Helper — Conditional Import Pattern (Required)
This project is **Flutter Web only**, but a bare top-level `import 'dart:html'` still risks compilation errors in tooling/tests that analyze non-web targets, and it isn't the Flutter-recommended approach for platform-specific APIs. **Always** split the implementation into a shared interface (`core/utils/pdf_download_helper.dart`), a web implementation (`..._web.dart`, the only file allowed to `import 'dart:html'`), and a non-web stub (`..._stub.dart`), and import via:
```dart
import 'pdf_download_helper_stub.dart'
    if (dart.library.html) 'pdf_download_helper_web.dart';
```
> ❌ Never import `dart:html` directly at the top level of a shared file.

#### Media-Related Routes
Add to `core/router/app_router.dart`: `/cv` (inline PDF viewer) and `/project/:id/gallery` (fullscreen image gallery).

### 🚫 Media-Specific "Must NOT Do"
- ❌ Never autoplay video.
- ❌ Never initialize or preload a `VideoPlayerController` before the user opens that project or taps play — `autoplay: false` alone does not satisfy this.
- ❌ Never initialize, construct, or render a video player inside the home page's project cards (`projects_section.dart`) — cards show `thumb.png` only; video lives in Project Details.
- ❌ Never embed video as a raw HTML `<video>` tag — always use `chewie`.
- ❌ Never store more than one copy of `cv.pdf` — single asset file only.
- ❌ Never import `dart:html` directly — always use the conditional import pattern.
- ❌ Never load all project screenshots eagerly — always lazy load.
- ❌ Never load full-resolution screenshots in the projects grid — cards use compressed thumbnails only.
- ❌ Never ship an uncompressed or oversized PNG/JPEG — compress and use WebP/AVIF where supported.
- ❌ Never forget to `dispose()` the `VideoPlayerController`.
- ❌ Use only `mp4` for video — no `webm`, `ogg`, or other formats.
